Overview

One Table, Four Views of the Truth

You'll build a customer table full of synthetic PII, then layer on Snowflake governance controls so administrators, analysts, support agents and marketers each see a different, policy-driven version of the same data.

1

Discover

Sensitive data classification scans columns and detects names, emails, SSNs and more, then applies system tags automatically.

2

Mask

Dynamic masking policies transform values at query time based on the active role. The stored data never changes.

3

Filter

Row access policies decide which records a role can see at all, for example hiding VIP and internal accounts from support.

4

Scale

Tag-based masking and secure views carry protection to new columns and consumers without you writing a policy for each one.

PII_ADMIN

Data owner. Sees every value in every row.

PII_ANALYST

Sees all rows, with partial values good enough for analytics.

PII_SUPPORT

Full contact details, but only for STANDARD customers.

PII_MARKETING

STANDARD and VIP customers, with identity and address hidden.

Prerequisites

Before You Begin

  • Snowflake Enterprise Edition or higher. Masking policies, row access policies, tag-based masking and classification all require it.
  • ACCOUNTADMIN, or <YOUR_ROLE> with CREATE ROLE, CREATE SCHEMA on the database, APPLY MASKING POLICY, APPLY ROW ACCESS POLICY and APPLY TAG on the account.
  • A warehouse (any size works). Replace <YOUR_WAREHOUSE> in the script.
  • An existing database to hold the demo schema. Replace <YOUR_DATABASE> in the script.
  • A Snowsight SQL worksheet. Paste each step and run it, or run the downloaded script top to bottom.
1
Step 1

Create the Schema and Table

This step creates a dedicated DEMODATASECURITY schema and a CUSTOMERS table whose columns cover the common PII categories: names, contact details, government IDs, addresses and financial data. Grouping the columns by sensitivity makes it easy to see which policies protect what later on.

2
Step 2

Create Roles and Grants

Here you create four functional roles and give each one identical SELECT access to the table. Because the privileges are the same, every difference you see later comes from governance policies, not grants. The roles are granted to ACCOUNTADMIN so you can switch between them in one worksheet.

3
Step 3

Define Masking Policies

Each masking policy is a small SQL expression that runs every time the column is queried and returns a value based on CURRENT_ROLE(). Policies can do more than hide a value: they can reveal the last four digits, truncate a date to its year, or keep only an email's domain, so analysts still get useful data.

4
Step 4

Define a Row Access Policy

Masking controls what a value looks like. A row access policy controls whether a row is returned at all. This policy reads CUSTOMER_TYPE so that support agents only see STANDARD customers and marketing never sees INTERNAL test or employee accounts.

5
Step 5

Apply the Policies

Policies are standalone schema objects, so you attach them to columns and tables with ALTER TABLE. One policy can protect many columns (mask_phone covers both phone fields), and you can change a rule later without touching any query or dashboard.

6
Step 6

Load Synthetic Sample Data

This step inserts 98 fictional customers: 58 STANDARD, 25 VIP and 15 INTERNAL. Policies apply at query time, so it doesn't matter that the data loads after they're attached. The verification query, run as ACCOUNTADMIN, confirms the full load.

7
Step 7

Classify Sensitive Data

SYSTEM$CLASSIFY samples the table and recommends a semantic category (NAME, EMAIL, US_SSN…) and a privacy category (IDENTIFIER, QUASI_IDENTIFIER, SENSITIVE) for each column. With auto_tag enabled, those results are written as system tags, giving you a searchable inventory of where PII lives.

Classification results can vary slightly with the sample. Review the recommendations before you rely on them for policy decisions.
8
Step 8

Tag-based Masking

Instead of attaching a policy to every column, you attach one policy to a tag. Any string column that gets the PII_LEVEL tag is protected automatically, so new columns are covered the moment they're tagged. Where a column already has its own policy, that direct policy takes precedence.

Before vs. After: Tag-masked columns

9
Step 9

Role-based Secure View

A secure view gives a team a purpose-built slice of the table. Marketing gets only the ten columns it needs, and the masking and row access policies on the base table still apply through the view, so the two controls reinforce each other.

PII_MARKETING querying CUSTOMERS_MARKETING_V (Customer #1)

10
Step 10

Test as Each Role

Switch roles and run the same query to see governance in action: one table, one query, four different results. The row counts at the end show the row access policy working alongside the masking.

11
Step 11

Clean Up

When you're done, uncomment and run this block to remove everything the demo created. Unset the tag's masking policy first, then drop the schema to remove the table, view, policies and tag together. The four roles are dropped separately because they are account-level objects.

Wrap-up

Key Takeaways

You protected PII without copying data, changing applications or maintaining separate tables for each audience.

Policies follow the data

Masking and row access are enforced in every tool, whether that's Snowsight, BI, notebooks or apps, because they live on the table, not in the client.

Useful, not just hidden

Partial masking (last four digits, year only, domain only) keeps data analytically valuable while removing what identifies a person.

Discover, then govern

Classification shows you where PII is. Tags turn that inventory into enforcement at scale.

Centralized and auditable

Rules are defined once as schema objects, so they're easy to review, change and audit.
